watches: **what the runner containers leave behind on the Mac's disk** (operator decision 2026-11-23; measured the same day: Colima's data disk had grown to 99 GB and free space on the Mac to 23 GB of 460 GB, of which the 12 runner containers held unrotated json-file logs 6 GB (one 2.7 GB), `_work/_update` staging 459 MB each, superseded `bin.<ver>` and `externals.<ver>` dirs, thousands of `_diag` logs and regenerable caches), by `bin/ci-runners.sh tidy` on every RUNNING runner container (`*-linux`, `*-linux-N`, `harbor-gate`; fleet, org, extra and governance alike). ALWAYS removed, busy or idle: `_work/_update*` (unless touched in the last 10 minutes, a self-update in flight), the `bin.*`/`externals.*` dirs the live `bin` and `externals` symlinks do not point at (a home with no such symlinks is left whole), `_diag` logs over 3 days old, and the container's json log truncated in the VM when over the cap it is created with (`logsize`, default 20m; harbor#1060). Only when the runner is IDLE (no process `Runner.Worker` inside it, read again before each directory, never `pgrep -f`, which matches its own `sh -c`): `.cache`, `.npm`, `_work/_tool`, `.bun/install/cache`; and never while the network is METERED (`status-network.sh`'s mode file), since a cache removed is a download again. It ends with `fstrim -v /var/lib/docker` in the VM, because deleting inside the VM frees nothing on the Mac until it trims (99 to 25 GB; its `fstrim.timer` is enabled and had not), and reports the MB the Mac gained from `du` of the datadisk before and after. The same change makes every container `create` runs start with `--log-opt max-size=20m --log-opt max-file=2` (`logsize SIZE` and `logfiles N` in `~/.claude/.harbor-ci-runners`, `HARBOR_CI_LOG_SIZE`/`HARBOR_CI_LOG_FILES` over them), so the logs stop regrowing; an existing container keeps its old log config until `refresh --apply` recreates it
schedule: **Sundays from 04:00 local, inside `status.fleet-snapshot`'s run** (operator decision 2026-11-23: weekly, Sunday about 04:00; no launchd job of its own): the last step of `bin/status-fleet-snapshot-refresh.sh`, `ci-runners.sh tidy --apply --if-due`, which is a no-op until NOW is past the latest Sunday 04:00 and no completed run (`cache/ci-runner-tidy.stamp`) is as new, so a Mac asleep at 04:00 runs it at the next tick and a run covers the whole week; a box with no stamp is seeded and first runs the next Sunday. By hand: `sh bin/ci-runners.sh tidy` is a dry run and says what it would do, `--apply` does it; falsifier: `sh tests/ci/runners/tidy.test.sh` (the tidy script run for real against fake runner homes through a stubbed docker and colima: the always-safe set gone and the live dirs, symlinks, checkout and registration left; a busy runner losing only that set; a job starting mid-run stopping the cache removal; a metered network keeping the caches; the dry default removing nothing; a log at exactly the cap kept and one byte over truncated; a log path outside docker's containers dir never handed to sudo; a failing runner, fstrim, colima or docker; the MB freed from a datadisk that shrinks; the due gate at 03:59:59, 04:00:00, later that Sunday, Wednesday, the next Sunday, a missed Sunday and a seeded stamp; the create argv carrying the log flags, from the default, the config and the environment)
notifies: **One `[check:ci.runner-tidy]` line in `~/.claude/cache/checks.log` per `--apply` run** (`12 runners, 5900 MB of json logs truncated, 71680 MB freed on the Mac (datadisk 99840 -> 28160 MB)`, or `, caches left (metered)`), never one per tick; the dry run prints what it would do and writes nothing. Per-runner lines go to the terminal of a hand-typed run (`ok: <c>: update=1 versions=2 diag=3412 caches=4`; `<c> is running a job` when its caches were left). No desktop notification and no statusline word of its own: the disk it protects is `status.disk`'s `DISK LOW`
red: a runner could not be tidied or the VM could not be trimmed (exit 1 and a FAIL line naming the container or `colima ssh -- sudo fstrim -v /var/lib/docker`: the Mac keeps what was deleted until it is run by hand), or the Mac is short of disk again (`DISK LOW`, check `status.disk`: `sh bin/ci-runners.sh tidy --apply` is its first answer). Docker not answering is `DOCKER DOWN`'s (`ci.runner-alarm`), not this check's: no stamp is written, so the next tick tries again.
