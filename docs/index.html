Architecture

Harbor

A governance layer for coding sessions on one machine. It answers a narrow question — what does the assistant know, and what can it do, at the exact moment it acts — and it answers it with mechanisms rather than documents.

What it is

Harbor is four layers wrapped around a coding assistant, each intervening at a different point in a session's life. They are independent: any one can be removed without the others stopping, which is deliberate, because a governance system that fails as a unit fails completely.

The four layers

  • The security floor. Hook-invoked guards that refuse tool calls: pipe-to-shell, writes to protected instruction surfaces, egress carrying identity or secrets. It is the only layer that can say no, and it is written in POSIX sh so that it still runs when everything else is broken.
  • The injector. Declarative rule packs that deliver a sentence to the model at the moment it acts rather than at the top of a session. This is the layer the rest of the document spends the most time on, because a measurement says it is the one that changes behaviour.
  • Governance and the record. The harbor CLI, the session work-log, and the marker mechanism that decides which repository's rules govern a given session.
  • Doc-truth. The lint rules, generated documents and CI jobs whose only job is to make the other three layers' claims about themselves checkable. This page is part of that layer.
The governing idea

A rule with no mechanism is a wish. Every claim Harbor makes about itself names the thing that fails when the claim stops being true — a lint rule id, a test case, a CI job, a guard. Where nothing enforces a rule, that is stated rather than implied. The tables on this page are generated from the repository for the same reason: a count written into prose is a copy, and copies drift while reading perfectly.

The finding the architecture is built on

Harbor's shape is not a preference. It follows from a measurement that overturned this project's own earlier conclusion, and everything expensive in the system exists because of it.

A rule that is resident when the model acts binds. A rule it would have to remember does not. The same sentence, in the same session, against the same task: written into the project's instructions it was obeyed 0 times out of 4; delivered at the tool call it was obeyed 4 out of 4.

Three consequences, each measured separately

More constitution does not fix it. Against a convention-shaped prompt injection, the full constitution — with its security section present and complete — scored 0 out of 6 once the injected text stopped sounding like an injection and started sounding like routine project bookkeeping. The injector's detector, wired at the tool result with no constitution at all, scored 6 out of 6 in the same cell. The channel was the variable, not the prior.

Shorter constitution does not fix it either. Four constitutions from 0 B to full size, same rules appended in the same position: compliance is a step function at "the rule is present", not a slope on length. Trimming buys cost, not obedience.

But scoping has a reach cost, and a pointer buys it back. Moving instructions from the box into individual repositories makes the always-on surface flat as projects multiply — at ten projects a box-level layout would spend more than the entire context ceiling on skill descriptions alone. The price is that a session standing outside the repo can no longer see them, and one small box-level pointer naming the repo restores the reach.

What this does not license

These are one task family, one model tier, and one detector vocabulary. The detector catches text that addresses whatever is processing it; an injection phrased entirely outside its phrase lists is not measured and is not claimed. It is a net, not a wall — and the security floor's own record says the same about its egress rules. The measurements are reproducible from EVALS-DATA/, envelopes included.

The security floor

The floor is the only layer that can say no. It is a set of hook-invoked guards that inspect a tool call before it runs and refuse it — pipes into a shell, writes to the files that govern future sessions, outbound traffic carrying something secret-shaped.

It is written in POSIX sh and nothing else, and that is load-bearing rather than nostalgic: the floor has to run on the day the runtime is broken, the package manager is mid-upgrade, or a session is being recovered from a machine that will not boot its usual toolchain. Everything it depends on is in a base install.

Three layers of deliberately different strength

The floor describes itself as defence in depth, not a boundary, and the distinction between its layers matters more than the sum of them.

  1. The deny list — the only layer the model cannot argue with, evaluated by the harness before any hook runs and un-swallowable in every mode. It binds the named tool: denying a write to a file does not stop a shell redirect to the same file. It is glob-based, so it cannot reason about command semantics at all.
  2. The guard hooks — text scanners over the command or the path. Strong against the shapes they model, hardened through two rounds of adversarial attack, and inherently approximate, because that is what a text scanner over shell syntax is.
  3. The integrity gate — stops nothing. It detects that the first two layers have been altered and refuses to open the session.

Each fails differently, which is the entire argument for having three. The real security boundary is credential separation and the operating system's sandbox; the floor raises the cost of an accident or a prompt-injected mistake and is not a containment proof against an attacker who already controls the session.

Two properties that are not the same thing

Fail-closed. A refusal is signalled by one specific exit code. Every way a guard can fail to run produces a different code — the JSON parser missing makes every field read empty and the guard allows everything; a deleted guard, a non-executable guard and a syntax error each exit with their own number. None of them is the refusal code, so none of them refused, and the floor still looked installed, pinned and wired throughout. A wrapper now sits in front of the chain and maps anything that is not an explicit allow to a refusal. A guard that cannot execute must not read as permission.

A kill-switch on the first live line. Every guard begins with the same environment check, before any other logic, so that an operator locked out by their own floor has one documented way back in. This is checked by lint — a guard whose first line is anything else fails the build. The reasoning is the last rule in the constitution's verification list: a guard that blocks ordinary work gets switched off by hand, and a disabled guard protects nothing. Making the escape hatch official is what stops it being improvised.

B8 — pinning the instruction surfaces

The subtlest guard is the one that watches what will be read rather than what is being run. Files that load into every future session — the machine's instructions, its skills, its commands, its hooks, its rule packs — are hashed and pinned, and drift is reported at session start with the paths that changed.

Found by checking rather than assuming

The pinned surface list did not include the injector's rule packs until it was audited on the branch that built them. A rule pack is text injected verbatim into every future session at the moment of an action, which is arguably the sharpest instruction surface on the machine, and it was the one nothing reported. It is covered now, verified end to end in a sandbox: install, pin, edit a pack, see it named as drift by path.

Re-pinning is deliberately not automated. An installer run from a session that blesses its own instruction surfaces is a self-approval loop, so the pin is a command the operator runs from their own terminal. This is the general rule stated once: the system may observe continuously and propose in batch, but it may not promote its own observations into a guard, a lint rule or a deny list without a person approving the change.

What it does not claim

The repository keeps a record of measured bypasses of its own egress rules. That document is not an embarrassment being managed; it is the reason the floor is described as a net rather than a wall, and the reason judgment is still load-bearing on top of it. A layer that claimed completeness would be the more dangerous artefact, because the next person would stop looking.

The live state is also not taken on trust from any document, including this one. harbor verify answers "is the floor on?" by firing shapes that are known to be blocked and checking that they were, because a page describing machine state is a copy — and the constitution's own paragraph about the egress scanner asserted the opposite of the truth until it was checked.

The cloud rules are an allowlist of named commands, so an unnamed vendor is uncovered

The destructive-cloud guard recognises the command-line tools of one cloud vendor by name. That is a deliberate scope — the rules encode which subcommands of those tools destroy data, and that knowledge does not generalise — but it means a different vendor's tool, an orchestrator, or an infrastructure-as-code binary passes this layer untouched, however destructive the verb. The same shape holds for the branch-protection rule: it recognises the flag spelling of a force push, and the refspec spelling of the same operation is a different string. Neither is a bug in the rule that exists; both are the boundary of the set of rules that exist, and the honest place to read that boundary is the guard's own source rather than a summary of it.

Measured 2026-08-29 — what passes untouched, with the controls that make the negatives mean something

An independent probe fed hostile shapes to the guards as text and read the verdict. Two controls fired as expected — the flag spelling of a force push to a protected branch, and a recursive dataset removal — so the following allowed results are not an artefact of a broken harness:

  • the same force push written as a refspec, plus the mirror and delete-branch spellings of the same operation
  • every non-Google cloud tool: an orchestrator deleting a production namespace, an infrastructure-as-code destroy, a bucket removal on another vendor
  • the physical macOS paths behind the firmlinks, where the logical spelling of the same directory is blocked
  • the whole configuration directory leaving the machine in an archive — the egress rules key on key-material paths and provider-secret patterns, not on that directory

None of these is a rule behaving wrongly. Each is the edge of the set of rules that were written, which is why the guard's source is the honest place to read the scope and a summary is not.

The false-positive rate is the number that decides whether any of this survives

Same probe, sixty ordinary commands: one denial. A further sweep found six more, and three of them blocked real work during the session that ran the probe — a documentation heredoc containing a substitution pattern, a test string quoting a dangerous command as an argument, and a shell pipeline feeding data into a guard script. That last one only reproduces when a command substitution folds, so the message cannot lead you to the offending text: no single line triggers it. Also still denied is the archive-extraction step of the recovery path this floor itself prescribes.

This is the failure mode the constitution names directly — a guard that blocks ordinary work gets switched off, and a disabled guard protects nothing. A rule that fires on prose is not a stricter floor; it is a floor with a shorter life.

One property does generalise, and it is the reason a soft verdict is safe here: a rule that would ask a human escalates to a refusal when no human is reading. A confirmation prompt raised inside a subagent, where nothing can answer it, would otherwise resolve itself — an approval nobody gave. The guards detect that they are off the main loop and deny instead. This is a property each guard has to carry deliberately; a hook that predates the convention, or comes from another project, does not inherit it.

The injector

The injector turns governance into data. A rule is a markdown file with YAML frontmatter; adding one is writing a file, not editing a hook. Wiring happens once per machine, and from then on the number of rules and the number of projects grow without touching any code.

Two tiers, discovered from where the session is standing

The predicate vocabulary

Read from the vocabulary gate in bin/inject-hook.sh: always cmd-prefix cmd-contains path-contains content-contains repo-has tool-is source-is injected-instruction — plus not <predicate>, which inverts any of them.

It is fixed, and it is not a language. Every predicate compares a value from the payload against a pattern from the pack, and the payload value is only ever the subject of a case — never the pattern. Nothing from a payload is evaluated, interpolated into a command, or used as a glob.

Why an unknown predicate refuses both ways

An unrecognised predicate does not fire, and it does not satisfy not. The first version returned the same "did not match" for both, so not cmd-prefx git push — one letter wrong — inverted a never-matching typo into a rule that fired on everything. The most likely typo must not produce the loudest possible rule. Lint IJ1 now rejects the typo at commit time, which is the only place it is cheap to catch.

Additional context is accepted on some hook events and rejected on others — and rejection discards the whole object, including an operator message riding along in it. PreCompact in particular has no channel to the model at all. A pack shipped on it, and every compaction on this machine threw its note away while the test suite stayed green, because the suite asserted the engine's output rather than what the harness accepts. The rule moved to SessionStart with source-is compact — the far side of the same moment, where it can be heard — and lint IJ1 now fails any pack that targets a context-less event without declaring an operator audience.

Repetition, and why the default is once

once: session is the default because a note repeated on every Bash call stops being read by its third appearance. That is not a cosmetic problem: it is a guard being tuned out rather than switched off, and nothing turns red either way. once: match re-fires when the subject changes, and once: never fires every time — which only a rule about a rare moment should use.

"Subject" is resolved in three steps: the file path the tool was given; otherwise the content written or returned; otherwise the raw command. It is the raw command and not the matched prefix, because gh pr merge 174 and gh pr merge 179 are different acts on different objects and a rule should speak for both.

The third step was missing, and the failure was silence

Until 2026-08-09 the subject stopped at content, so a PreToolUse rule over Bash had no subject at all — nothing is written or returned before the call — and once: match silently behaved as once: session: the first matching command spoke and every later one, however different, got silence. Measured with five differently-shaped commands in one session; only the first fired.

That is the quietest possible failure for the most natural pack anyone writes, cmd-prefix plus match, and nothing turned red for it. The claim on this page previously went further than the code and said match keyed on "a different command" — it never did. Fixed in harbor#180 and pinned by three arms in tests/hooks/inject-hook.engine-test.sh: first delivery, silence on a repeat, and delivery for a different command in the same session.

The ledger is keyed on the session id and lives in one file per session, sharing nothing between them. Concurrent sessions on this machine are normal, and the hostname here intermittently answers something else, which has already forked host-sharded ledgers in this estate. Session ids are validated before they reach the filesystem, and the directory is pruned on the way past.

The injected-instruction detector

One pack is different in kind: it reads what a tool returned and asks whether the content is addressing whatever is processing it, rather than a human reading it. That is the tell, and it is close to the only reliable one — an injection does not have to look hostile. The measured failure that motivated it is in the finding above: an HTML comment shouting SYSTEM DIRECTIVE was refused every time, while the same demand written as a plausible documented convention got past the full constitution.

Two phrase tiers, because one list would have to choose between missing the quiet shape and firing on ordinary prose. Loud phrases are unambiguous and fire alone; quiet phrases are individually innocent and need corroboration — two of them, or one plus a write-or-exfiltrate marker.

Its known false positives

Any content-based detector fires on documents about itself. Four tracked documents that discuss the attack are allowlisted, and the suite sweeps every tracked markdown file against that list in both directions, so a new false positive turns the suite red on the commit that introduces it. The runtime has the same property and it is not allowlisted away: reading the engine's own phrase list — grepping bin/inject-hook.sh — fires the detector, correctly by its own rule and uselessly in fact. Two loud phrases were already narrowed after they were found firing on pytest --help, two man pages, an OAuth client's "you are now able", and a package manager's contributor docs. Suppressing the self-referential case would mean weakening the match, which is the one repair this system does not make.

What it deliberately cannot do

There is no deny mode. The injector only ever adds text; vetoing a tool call belongs to the security floor, which is a separate layer with a separate installer and a much smaller, auditable surface. The measurement supports the split rather than merely permitting it — informing scored better than vetoing on the same fixture, because a veto stops the action without changing the decision that produced it.

Notes carry a per-session provenance stamp, derived from a machine-local salt and the session id, so a line claiming to be governance can be told apart from a line that merely says it is.

The engine was proven; the rules it ships were not

The engine's own suite carries well over a hundred assertions, and every one of them runs against a pack the suite writes itself in a temporary directory. That is the correct way to test an engine — and it says nothing whatsoever about the packs actually shipped. Measured by matching every tracked note identifier against every suite by name, the large majority were named in none of them.

What that blindness cost is concrete. A project pack was added two days after the last seeding run, so the tree it was meant for never received it, and the note warning that a particular refresh flag destroys years of irrecoverable history had never once been delivered. Every suite was green throughout, because no suite looked.

Every shipped note must have a row, and both arms of it

A second suite now drives the real packs through the real engine, off a fixture of situations. A tracked note with no row fails the run — so a pack added with no probe cannot go green — and exemptions are listed with the reason each one cannot be pinned there, with their count printed on every run, because a silent cap reads as full coverage. Each note needs a silent arm as well as a firing one: a fixture that only asserts firing cannot see a false positive, and a guard that fires on ordinary work gets switched off.

It plants no violation, and does not need to

A suite over a guard has to break the guarded thing to see red. A suite over notes already has the positive assertion: if a shipped predicate breaks, its own firing arm goes red on the next run with no mutation step. The verdict machinery itself was checked by jamming the detector — stuck reporting "fired" it fails dozens of assertions, stuck reporting "silent" it fails dozens of different ones, and correct it passes them all. The two arms constrain each other in both directions, so the scoring cannot break quietly.

A fixture written beside a pack cannot see that pack's blind spots

Both suites above are necessary and neither is sufficient, and the reason is structural rather than a gap someone can close by adding rows. Whoever writes a pack writes its probe from the same mental model, so the fixture asks the situations the author already thought of — which is why it goes green while the predicate is wrong about a case nobody imagined. An independently authored probe, firing shapes the fixture does not contain, is a different instrument and finds a different class of defect: predicates that share a name with an engine helper but re-implement a weaker version of it, and packs whose declared tool scope is narrower than the events the harness already delivers to them. Neither is visible from inside a green run.

Measured 2026-08-29 — three defects both suites were green through

An independently authored probe drove every shipped pack through the real engine with situations the fixture does not contain. All three suites stayed green throughout; each of these was then confirmed at source:

  • One predicate skips the quote-blanking the others get. The prefix predicate reaches it through the segmenter; the substring predicate calls only the heredoc stripper. So a warning about a destructive database flag fires on a commit message that merely mentions the flag.
  • A pack's declared tool scope is narrower than the events it receives. The injected-instruction detector lists four tools. The wiring already delivers search results and every external-integration tool result to the engine, and its own sibling pack declares that wider set — so the detector for content that addresses the agent does not run on the tool results most likely to carry it. One line in the pack, no re-wiring.
  • A pack re-implements an engine helper, weaker. The bare-variable rule blanks double-quoted spans only, while the engine's own routine handles both quote characters — so it fires on a single-quoted query program, where the dollar sign is not a shell variable at all.

The first and third are false positives and the second is a coverage hole, and none is visible from a green run: the fixture asks the situations the pack's author already had in mind.

Detect and defer

Several repositories on this machine carry their own governance. When a session is standing inside one, the machine-wide rules stand down and the repository's own rules win. That deferral has to be one signal that every layer reads identically, or the layers disagree about who is in charge — which is worse than either answer.

The resolution is a walk up from the working directory looking for a marker, and it has three properties worth stating because each was a decision:

  • The innermost marker wins for nested repositories.
  • Ambiguous resolves toward the repository for anything that writes the machine-wide log. When it is unclear whether a session is inside a governed tree, the safe answer is the one that writes less.
  • The marker's value is constrained to two spellings, because for a key that three implementations in two languages read, the realistic failure is not a missing key — it is a near-miss value that looks marked to a human and resolves to nothing in code.
The seam's open edge

Deferring to a repository's own governance means trusting the copy of the guard that that repository deployed — and a scaffolded repo keeps whatever version it was born with. One tree on this machine still runs a production guard from before a security fix landed six weeks earlier, because nothing back-fills a deployed hook after creation. An advisory lint rule compares every deployed copy against the authoritative one and names the direction of the difference, which is the only reason this is visible at all. It is advisory because it reads paths outside the repository, so it reports and never turns the build red.

The work-log

Sessions write a record at their end: what was worked on, in a host-partitioned file, committed and pushed to a private repository. Two design points carry most of the value.

The push gate is fail-closed on secrets and fail-open on network. A secret scanner runs before anything leaves the machine, and a finding — or a missing scanner — stops the push. A network failure does not: the commit stays local and the next session's push retries it. Those two failures deserve opposite defaults, and collapsing them into one behaviour would either leak or lose the record.

Sessions that never reached the end are reconciled separately. A crash, a kill, or a sleeping machine means the end-of-session hook never ran. A second pass compares the log against the transcript index and writes a record for any session that is missing one, reading only filenames, directory names and modification times — it never opens a transcript.

A hazard this machine actually has

The record is partitioned by hostname, and the hostname here intermittently answers something else. That flip has already forked host-sharded ledgers in this estate, so anything reading the log must union both host directories rather than trusting one. The injector's own ledger avoids the class entirely by keying on the session id instead.

Where state lives

The machine's configuration directory holds identity, credentials, session history and work-log content, and it is treated as permanently private: nothing from it goes to a public remote, a web tool, or any service that caches or indexes. The boundary is the directory root and applies to everything beneath it. What enforces it is a deny list in the machine's settings — which binds subagent tool calls too — the fail-closed scanner on the work-log push, and the egress guard wired over both the write tools and the network channel, so it sees both halves of an exfiltration path.

Doc-truth

A governance system's documents are part of its attack surface. If a page says there are eighteen rules and there are twenty-one, a reader cannot tell which other sentence is also stale — and the failure is invisible, because the wrong number reads exactly as well as the right one.

A sweep of this repository once found the same fact stated differently in three documents, repeatedly. None of them were lies when written. They rotted.

The rule, and the three things that enforce it

Do not state a fact that lives somewhere else — derive it. A count, a status or a path written into prose is a copy. So there is exactly one generated document that states numbers about this repository, and any other document that wants a count links to it instead.

  • T1 fails when the generated status document is stale.
  • T2 fails when any other document states a countable claim in numerals.
  • T3 fails when a path cited by a tracked document does not resolve.

Two exemptions are deliberate: dated records of what was true at a given pass. Their numbers are evidence about a moment, not claims about now.

This page is in that system

Every table on this page is generated from the repository at build time by bin/docs-gen.sh. The prose is hand-written in docs/src/*.html and is where improvements go; the inventories are holes the generator fills. The page is built on demand (sh bin/docs-gen.sh --apply) and not committed, so it has no stale copy to drift; sh bin/docs-gen.sh --check fails when it cannot be built. An unknown hole is a build failure rather than an empty space — a section that silently renders as nothing is how a document loses a chapter without anyone noticing.

A rule with no mechanism is a wish

The test applied to every rule in this system: name the thing that fails when this is broken. If nothing does, it is documentation, not a rule, and it gets labelled that way rather than dressed up. Some rules genuinely have no mechanism — no lint can read a response, so the requirement to give a critique alongside the work is unenforced and says so in its own text.

Where a fix belongs is decided the same way, by structure rather than by convenience:

The thingWhere it lives

Something that must be enforceda lint rule, a CI job, a pre-commit hook
A guard's behaviourthe guard, plus a pinned assertion in its suite
A cross-repository seama frozen contract plus a fixture both sides run
A durable fact about the worldthe work-log

Measured 2026-08-29: every rule sampled can still fail, and the gaps are in what they look at

A green linter is worth exactly as much as its ability to go red, so the rules were mutation-tested against a throwaway copy of the tree: plant the violation each one guards, watch it fire, revert. Two dozen rules across both linters were sampled and every one went red. Two apparent non-fires turned out to be documented design rather than dead rules — one is advisory on the base branch by intent and blocking elsewhere, and the other ignores a row it cannot parse while carrying a floor that fails loudly if the row format ever changes wholesale.

No dead rule was found. What was found is that the rules are narrower than the prose they are trusted to police, in three specific ways.

Three coverage gaps, each with a live instance except the last
  • The count rule reads markdown only. A number written into a build file's comment or a shell script's header is outside it — and the build file currently states a script count that the repository passed some time ago, having grown by roughly a fifth since.
  • A count spelled as a word rather than a numeral evades it. Two documents understate the number of guards in words. One of them does so in the same sentence that asserts the count is stated nowhere but the generated file — which is the evasion the coverage document itself describes, committed in the document describing it.
  • The generalised path rule is narrower than the rule it generalises. The constitutional check learned to read both citation forms — the markdown link and the backticked path — when the decision was taken to cite repository-only documents in the second form. Its generalisation to every tracked document still parses only the first. Every backticked path outside the constitution was checked by hand and all of them are prose rather than citations, so the gap is real and currently empty.
A verifier is red right now, and it is wrong

The citation checker exits non-zero on a configuration value containing a wildcard — it fetches the literal string, receives a not-found, and reports a broken citation. The rule that scans for the same thing already skips wildcards; the checker does not, and a comment in the linter states that the two share one skip-list. They do not, and the difference is that single pattern. This matters more than the one false row: the whole value of a verifier is that its verdict is believed, and one that cries wolf gets its exit code ignored, which is the same failure as a test that cannot fail arriving from the other direction.

An advisory gate is a report, not a gate

The index of the skills a session cannot see is generated, and it is stale against the machine right now — two skills exist that it does not name. The rule covering it is advisory, so nothing fails. That is the correct severity for a surface whose truth depends on machine state a build cannot read, and it is also the reason this particular file drifts: the only thing standing between it and a reader is somebody noticing a line in a report.

This page's own generator has a blind spot, and it fails safe

The command that lists every derived hole and whether it is filled matches token names conservatively, while the code that fills them accepts any name. A hole whose name contains a digit is therefore invisible to the inventory — but still a build failure, because an unknown token stops the generation rather than rendering nothing. The audit tool under-reports; the gate does not. That is the correct direction for the pair to disagree in, and it is worth knowing which one to believe.

Change-class selection, and the direction it fails in

A docs-only pull request does not need the shell-guard corpus. A selector reads the changed paths against a declared mapping and runs only the suites that could be affected. Every uncertainty it meets resolves to running everything — a broken selector then costs CI time rather than coverage, which is the only acceptable direction for that failure.

Jobs run even when their dependency failed

A continuous-integration system skips a job whose prerequisite failed — and a skipped required check does not block a merge, because nothing about it reads as failing. A red suite could therefore hide behind a check that looked satisfied precisely because it never ran. The fan-in jobs here run regardless and decide for themselves, which is the same defect class as a test that cannot fail.

Two things learned the expensive way

A cancelled check scores as a failure and never clears. Not as pending, not as neutral — as a permanent red that blocks every merge until the workflow that produced it is changed. This cost a morning here, and the merge backstop now uses the platform's own required-check oracle rather than reimplementing the scoring, because that oracle already encodes the rule.

Branch protection can lapse silently. On some plan and visibility combinations the protection endpoint simply returns an error, every rule stops applying, nothing turns red, and the next red merge succeeds. The backstop therefore checks that protection exists, not only that the checks are green. An override is written into the merge commit rather than only the terminal, because "was this merged red, and did someone decide that?" is answerable six weeks later only from the history.

A test that cannot fail is worse than no test

This is the rule the rest of the quality layer is organised around, and it is enforced by habit and by mutation testing rather than by a linter: break the thing a test guards, watch it go red, restore. That is the only evidence a test tests anything.

It is not hypothetical here. The injector's compaction rule had a passing assertion for its entire broken life, because the assertion checked that the engine produced output rather than that the output was accepted. A second class is quieter still: a group of silence-assertions once sat above the fixture whose absence they would pass without, making every one of them vacuous — exposed only because the paired must-still-fire half went red. Falsification proves discrimination, not correctness, so a new rule is asserted in both directions: the shape that must fire, and the near-miss that must not.

Skills and the always-on surface

Skills are capability packages a session can invoke. The architectural question is not what they do — it is what they cost when they are not used.

An ambient skill's description loads into every session so the model can decide to reach for it. An invoked-only skill loads nothing until it is called by name. The difference is a single frontmatter key, and it is the difference between a skill that costs bytes on every turn of every session and one that costs nothing until wanted.

A second tier arrived from outside, and it is dispositioned, not adopted

A separate set was vendored from an upstream repository and de-platformed. None of it was adopted on arrival. Each one was sorted into a disposition — a cheap conversion, a rewrite because the body is shaped for a platform this box does not run, or a hold — and a held skill carries a banner in its own body saying so.

The question a held skill has to answer before the banner comes off is not "is this good" — it is what would this have changed in a task we actually ran? Until that has an answer with a worked example, the file is reference rather than instruction. Holding is cheap and reversible; adopting a method nobody has tested against real work is neither.

The surface has a ceiling, and it is checked

Descriptions stack, and they stack with projects. Measured on this machine: twelve ambient measurement skills cost around 5.7 KB of description, and extrapolated to ten projects a machine-wide layout would spend more than the entire always-on ceiling on descriptions before any instructions exist. Scoping skills to their repository makes that slope flat. An advisory lint rule reports how close the current surface is to its ceiling, so the trend is visible before it is a problem.

Frequency was the factor every cost argument was missing

Every argument about whether a skill earns its bytes was being made without the one number that decides it: how often it is actually invoked. That number is now measured by reading the session transcripts directly — most installed skills have never been invoked at all.

Why it counts from transcripts and writes nothing

A usage counter would be a distilled second copy of what the transcripts already record exactly, and a second copy is the thing this repository spends most of its lint budget preventing. Reading the source of truth on demand is slower and correct. It also means the measurement cannot drift, be forgotten, or quietly stop being updated — three failure modes a ledger has and a query does not.

The trap this measurement exists to avoid

An invoked-only skill with zero invocations costs nothing and is not evidence of anything. An ambient skill with zero invocations is paying its description on every session for a capability nothing has ever wanted. The two look identical in a list of names and are opposite conclusions, which is why the report labels the tier next to the count rather than ranking by count alone. The distinction is not academic: on this box the great majority of never-invoked skills are invoked-only and cost nothing, and the report's job is to surface the small remainder that are ambient and idle.

Zero invocations measured the tier, not the skill

The hidden tier was built on a fear: that a large roster degrades selection, so most skills should be removed from the listing and left readable but uninvocable. That produced a clean-looking argument for retirement — several skills had never once been reached.

The argument was circular, and a sweep killed it. Cases drawn from work actually done on this box were run against the whole installed roster with the hide flag stripped from the copies. Skills that had never been reached fired against real tasks — and a hidden skill cannot be invoked, so its zero was guaranteed before any work started. The decisive number is not how many fired but where they live: of the skills that fired on those cases, all but one are hidden from a session as the box stands today. Nothing false-fired and both negative controls drew nothing, which is the half that makes the result mean anything.

The first run of that sweep was contaminated, and the retraction is the lesson

The measurement tool fed each session the case file on standard input, so every prompt carried the whole fixture — the expected-answer column included. The leak manufactured exactly half the fire rate: fourteen fires became seven on the clean re-run, and two skills this page previously reported as standing did not survive it. The reasoning was wrong, not merely the conclusion. The check applied at the time was "is this skill named anywhere in the fixture?", and the leak's mechanism was never the name appearing in the prompt — it was several kilobytes of other people's tasks changing what the session did. Checking for the name tested the wrong thing and got the right answer twice by luck, which is indistinguishable from a working check right up until it is not.

The index is the route to what is not listed

A hidden skill cannot be suggested to a model, because nothing lists it — so a session cannot be reminded that it exists. What it can do is read a file. A single greppable index names every hidden skill and the path to read it, which turns "there is no skill for this" from a belief into a claim that can be checked. Whether that route is actually taken under ordinary work is not yet measured.

Descriptions that sell a method the model already has do not route

Several skills were listed, were handed proportionate tasks squarely in their own subject, and were never reached. The instinct is to blame trigger vocabulary. It was measured, and vocabulary was not the problem: the diagnostic case contained the target skill's own trigger words verbatim, and the session still did the whole analysis by hand.

Every one of those descriptions advertised a method the model already knows. Naming a well-known technique promises nothing that doing the work directly would not already deliver, so there is no reason to pay a tool call for it. Each lead sentence was rewritten to the differentiated outcome — what you end up with that you would not otherwise — lifted from the skill's own body rather than invented. Trigger vocabulary was kept and extended with phrasing natural to the task, deliberately not copied from the evaluation prompts, so the next measurement reads as routing rather than memorisation.

On the cases every sweep shares, distinct skills invoked roughly doubled. Two skills moved from being read to being invoked. One went the other way and lost a skill that had not been touched — which is the honest shape of a result at this sample size.

Held-out cases are the only thing that separates routing from keyword matching

Prompts targeting a specific skill, phrased deliberately differently and verified to share zero trigger phrases with that skill's own listing, are the measurement that counts. Three of five routed on meaning alone. One skill fired on the case whose prompt literally contained its own trigger phrase and drew nothing on the same archetype without the words — keyword matching wearing the costume of routing, and nothing but a held-out case tells the two apart. Another reached nothing in either phrasing across three sweeps.

One run separates a large effect from noise, and nothing smaller

The same case invoked a skill in two earlier sweeps and nothing in the latest; one naming task drew nothing while two others reached the same skill. A jump of several distinct skills is large enough to survive that; a single flip in either direction is not, and is reported as noise rather than as a finding. The sweep is also expensive — the estimate in the tool's own header was once wrong by two orders of magnitude and was planned off twice, so the measured figure is now printed by the dry run, where the decision to spend it is actually made. And it leaves no machine-readable trace: the results file is deleted unless explicitly kept, so every figure above survives as prose and cannot be re-scored without paying for the sweep again.

Measured 2026-08-29 — "never fired" is three different findings wearing one label

A count that merges the three reads as evidence about skills and is mostly evidence about the fixture.

Monitoring: what the box says about itself

A floor that cannot be observed is a floor nobody can tell is off. Every layer above answers what should happen; this one answers what did, and it is deliberately split by cadence rather than by subject — because the failure mode of self-monitoring is not missing data, it is a true statement shown so often that the reader stops seeing it.

Four rhythms, and why there are four

Each of these answers "what is true right now", and they differ only in when they are allowed to speak.

  • Every statusline tick — the numbers that move, over a cache, because a figure that changes between two glances is worth a glance.
  • Once per session, loudly — the verdicts that do not move: the work-log is dead, no guard is wired, the floor teeth drifted, the instruction surfaces are unpinned. Those stay true until a human fixes them, so a statusline row for them is wallpaper by the third session — and once the operator has learned to look past a row, that row can never carry an alarm again.
  • On demand — everything at once, rendered as a page, when the question is "what state is this box in" rather than "did anything change".
  • Between sessions — the health probe that runs when nobody is looking. The other three run only while the operator is already watching, which means a box left alone for a week reports nothing about the week.

The guard-decision ledger: write, read, judge

Three scripts, deliberately separated, because the thing that records must not be the thing that decides whether the record is bad news.

The writer runs even when the floor is switched off, and that is its entire point. Every guard opens with a kill-switch line, and the installer wires each of them through a single dispatcher — so under an override the wrapper returns immediately and the guard is never spawned: zero processes, zero rule evaluations, and nothing anywhere in the floor that could record that the operator walked past it. An override is the operator saying this rule is wrong with their hands instead of their mouth, which is the highest-quality feedback signal the system produces, and it was structurally unobservable. A hook that runs regardless of the switch is the only shape that can see it.

The writer is redacted by construction. Everything the reader can answer is answerable without any command text ever having been stored — which rules fire and how often, flat versus argv per rule, the override rate, and repeat blocks of the same shape. That last one is the interesting query: a rule blocking the same shape over and over is a false-positive candidate, and a guard that blocks ordinary work gets switched off, after which it protects nothing.

The judge is a third script — ten independent rules over one parsed record set, where no rule can affect another. Exit zero means nothing in the ledger says the floor is failing; it does not mean the floor is right.

The documents that are outputs, not sources

Several of this repository's own documents are generated — the counts file, the plan, and the architecture page you are reading — each with a lint rule that fails the build when it has been hand-edited or left stale. They are generated for the same reason: a count in prose is a copy of a fact that lives in code, and copies drift while reading perfectly. A sweep found the same fact stated three different ways in three documents, none of them wrong when written — one said eighteen rules where there were twenty-one, one said nineteen skills where there were twenty-eight, and one listed as open the risks another section of the same file said had shipped.

The same argument settled a second question: which of the plan was actually built. Asked once, three methods gave three answers — parsing the ticket document for "DONE" said several workstreams were open, parsing each ticket's whole block agreed, and probing for the artifacts found every one of them already existed. The prose and the repository disagreed and the prose lost. So that document is derived too.

Staleness is a priority signal, not a failure flag

A two-hundred-day-old contract may be exactly right. The per-document age report produces the question "still right?" rather than the verdict "wrong", and its age source is the version-control history, which already knows — so there is no second copy of a date to keep current.

The cost of being always-on is measured, against a recorded prior

Everything this repository loads into every session costs bytes on every turn, so the always-on surface is measured rather than estimated. The check compares today's figure with the last recorded measurement and fails when the deliberate surface has moved off it. It is deliberately not a ceiling: a ceiling is a number somebody invented, and it starts being argued with the first time real work needs to cross it.

Unavailable is not zero

The rendered page states no counts of its own — every figure on it comes from the generators, the staleness probe or the version-control history, at render time, and the page itself is git-ignored because it is output rather than source. It is self-contained: inline styles, inline vector graphics, no fonts and no network at view time, because the moment you most want to know what state the floor is in is the moment the connection is gone.

That property forces a rule. When the ticket source cannot be reached, the panel says so rather than rendering an empty chart. A burn-down showing zero open tickets because the network was down is the same class of lie as a test that cannot fail — it reads as good news, and a chart is a worse place for a stale number than prose is, because nobody greps a chart to find it.

External dependencies fail open, and silently

A missing JSON processor once made every guard exit zero on a recursive delete of the root filesystem — the floor did not fail loudly, it failed open. That one dependency was fixed; nothing enumerated the other nineteen. The dependency prober therefore names what breaks on every row rather than whether the binary is present, because "gitleaks: missing" is only the cheap half of the sentence.

Working on this

Four things this system is extended with, and what each actually costs — and one thing that happens before any of them.

Before building: resolve the frontier, in rounds

A design is a tree, and every decision branches into the decisions hanging off it. The frontier is every decision whose prerequisites are already settled — the questions answerable now, without guessing at answers not yet heard. Ask the whole frontier at once, numbered, each carrying a recommended answer. Each round the operator's answers push the frontier outward and unblock what depended on them. The session is done when the frontier is empty.

The earlier rule here was "up to three specific questions, one at a time". The cap was sound and the serialisation was not: independent questions do not need ordering, and paying a round-trip for each buys nothing while forcing the operator — who is holding the whole design in their head at that moment — to reload it once per question. Serialise only what genuinely depends on something. The cap that matters is on the frontier, not on the count.

Facts are yours; decisions are the operator's

When a frontier question needs a fact from the environment, go and find it — read the file, run the probe, dispatch a subagent. Never ask for anything you could look up. Do not block on it either: a running exploration is an unsettled prerequisite, so only the questions downstream of it wait. A question with no recommended answer is work handed back, and where one option deserves an argument against it, saying so carries more than four neutral descriptions.

The failure this replaces is premature completion

A vague bound — "understanding reached" — lets attention slip toward being done while branches sit unvisited, and everything built afterwards rests on assumptions nobody chose. An empty frontier is a checkable bound; a shared understanding is not. The reverse failure is real and cheaper to spot: a round that asks about branches the operator already settled reads as not listening. And a resolved frontier is not itself a licence to write — grilling is the read-only half.

Add a rule

Write a markdown file with frontmatter into a pack directory — the machine tier for something true everywhere, the repository's own tier for something true in one tree. Nothing else. No code changes, no re-wiring, no installer run for a repository pack.

Assert it in both directions in the suite: the shape that must fire, and the near-miss that must not. A rule with only the positive half passes for reasons unrelated to whether it discriminates.

Deploy a change

Installers are dry-run by default and require an explicit flag to touch the live configuration directory — a lint rule fails any mutator that does not have that gate, and a second one checks that every command a mutator prints is a command its own gate would accept. Seeding other repositories needs the flag a second time, because writing into trees outside the target is a different act from writing into the target.

Re-pinning the instruction surfaces is deliberately not automated and is run by the operator from their own terminal. An installer that blesses its own instruction surfaces is a self-approval loop.

Platform traps that have cost real time here
  • /tmp is a symlink, so two paths that are the same directory compare unequal as strings. Compare resolved paths. This has shipped twice.
  • The default grep on this machine silently skips binary and ignored files. Never rest a negative conclusion on it.
  • The shell that runs the floor is not the interactive shell. It does not word-split the same way, and an exit trap can turn an aborted script into exit zero — so check the return code of a deliberately broken call before trusting a green run.
  • Agents running in parallel share one scratch directory. Two agents writing the same filename is not a hypothetical.

Vocabulary — the words for shape and evidence

A fixed lexicon for the two questions this repository keeps asking: what shape is this, and does the evidence support the claim. Imported from complexity science and information theory, each term kept only where it names something Harbor already does in a paragraph.

Five structural words — module, interface, depth, seam, adapter — are defined in DOCTRINE/modularity.md and are not restated here. A definition stated twice is a copy, and copies drift while reading perfectly. This chapter adds the words that had no home.

Shape: modular and microservice are two axes, not one

The confusion this section exists to end is that modular and microservice sound like the same direction. They are perpendicular, and every combination of them occurs.

One moduleMany modules
DeepDeep monolith. Large implementation, small interface. Nothing wrong with it.Services. Each module deep, few seams crossed per task. The target.
ShallowBall of mud. Everything public, nothing hidden. Interface nearly as complex as the implementation. Distributed monolith. Many modules, each thin, all reaching into each other. The worst cell, and the one reached by splitting for its own sake.

Splitting a file moves one axis only. Cut a deep module into seven pieces and its hidden variety per symbol does not change — the same implementation sits behind the same symbols. What changes is how many seams a task crosses. So fragmentation is never evidence of modularity, and a file count is never evidence of either.

The falsifier for a seam

Cutting that deep module at arbitrary line boundaries makes the parts cost substantially more compressed bits than the whole, while cutting it along real function boundaries costs almost nothing. That gap is Dennett's criterion made operational: a boundary that costs bits is not a real pattern, and it can be detected without reading the code.

A real boundary is not a boundary worth crossing

The compression test answers whether structure exists at a file's own boundaries. It does not answer whether anything should be split, and treating one question as the other is how a measurement talks a codebase into fragmenting. Run across every file here over three hundred lines, the reality test alone marks 36 of 52 — every test suite included, because a suite genuinely is a flat list of independent blocks whose boundaries nothing crosses. The second question is the two-adapter rule made countable: symbols with at least two callers outside the file. Two files clear that bar, and under both conditions not one file earns a split.

The shared guard library is the instructive case: thirteen of its symbols are called from two or more other files, and its own function boundaries score below the reality threshold. It is correctly one deep library rather than a set of them.

Density, not edge count

Coupling has to be measured as the fraction of possible module pairs that actually call each other. A raw edge count cannot distinguish one shared deep library with many independent callers — a hub, which is the good shape — from every module reaching every other, which is the distributed monolith. Both produce large counts. Only density separates them, and the same trap catches destination entropy, which scores a pipeline and a mesh alike.

Harbor's own bin/ was measured against these definitions on 2026-08-30 and sits in the deep-and-fragmented cell with a hub topology: depth roughly a hundred lines per public symbol, near-zero call density, and the large majority of cross-file calls landing on the shared guard library. Both questions are re-derivable — bin/module-shape.sh, whose suite builds ten synthetic codebases and proves each lands in the quadrant it was constructed for. The suite is the load-bearing half: the instrument mis-measured four times before it settled, every one caught by a control rather than by review, and every one wrong in the direction that made a split look earned.
