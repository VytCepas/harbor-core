# CHECKS — the register of everything that runs on a schedule

One row per check. **A check that is not here is not built** — the constitution
rule this file exists for is in `CLAUDE.md` under "Fix the system, not your
notes".

Every check stamps its output `[check:<id>]`, so an alert resolves to its row
here and to the exact command that switches it off, without anyone opening the
source. `grep '\[check:' ~/.claude/cache/checks.log` is the whole alert history.

Measured 2026-09-04.

## Exit codes (D-29, D-49)

## Status is DERIVED, never written here

This table carried a `status` column until 2026-09-04 and **two of its seven rows
were wrong** — a client monitor read "written, not yet loaded" while `launchctl`
had it loaded and `checks.log` already held one of its stamps, and `cu-doctor`

a lie when written. That is the point: a status typed into prose is a COPY, and
copies drift silently while still reading correctly — `CLAUDE.md`, "Don't state a
fact that lives somewhere else — derive it."

So the column is gone and the box answers instead:

```sh
launchctl list | grep com.harbor      # PID (- = not running), LAST EXIT, label
```

A label absent from that output is **not loaded**, whatever a plist on disk
suggests. Two traps this command does not show on its own:

- **A green out-of-band run does not clear a red schedule.** `launchctl` reports
  the last exit of the job it ran; a check re-run by hand afterwards writes its
  own receipt and leaves that exit code untouched. Read the check's receipt
  (`cache/cu-doctor-state.json` and friends) for what the gate currently says,
  and `launchctl` for whether the SCHEDULE is healthy — they answer different
  questions and can legitimately disagree.
- **`RunAtLoad` means a bootstrap is also a run.** A check re-loaded by hand
  fires immediately, so a fresh exit code may reflect that, not the schedule.

## Every plist here is tracked, and lint X9 is what says so

The canonical plist for each row above lives in `launchd/`, and **lint rule X9
reads this table** — not a glob of that directory — to check two things: that
every registered id has a tracked plist, and that the installed copy under
`~/Library/LaunchAgents` still matches it. The registry is the list on purpose:
globbing `launchd/` would make an untracked check invisible to the rule that
exists to find it.

The plists are **templates** (harbor#630): launchd does not expand `$HOME`, so each one carries `@HOME@`
(and `@HARBOR_LOCAL_BIN@` where it names that root) in place of a home directory, and
`bin/launchd-render.sh` fills them from `CONTRACTS/roots.tsv` when the operator installs one. X9 compares the
installed copy with what the tracked plist **renders to** on this box, never with the template.

**The registry is one file made of two sources** (harbor#1149). Client monitors live in the private
layer (`CONTRACTS/private-layer.md`): their rows in `checks.md`, their plists in `jobs/`. Where that
layer exists, `bin/check-registry-generate.sh` inserts its rows at the two `<!-- private:... -->` lines
of this file, `runtime-install.sh` installs the result as `bin/CHECKS.md`, and X9 looks for a row's plist
in `launchd/` and then in the layer's `jobs/`. Where it does not exist, this file is the registry, byte for byte.

Measured 2026-09-06, and both directions were live. A client monitor had been
firing hourly since 2026-09-04 with a row here, a tracked monitor script in a workload repo, and
**no plist in any commit**; `pulse`'s installed copy was fourteen comment-lines
behind the repo, so this tree documented a delivery observation the box had never
been given. The 2026-09-04 incident below is why that is not tidiness: launchd
keeps the job it *loaded*, so a missing or stale plist reads healthy in
`launchctl list` and the loss first shows at reboot. Recovery there was one `cp`
only because the repo held the canonical copies.

X9 is advisory, for lint X2's reason — half of it reads the operator's home
directory, and no commit should be gated on the state of one machine.

## Incident 2026-09-04: the survey that wrote this file destroyed four agents

An earlier revision of this document reported the four daily agents as
pre-existing casualties of "a `plutil -replace` that targeted the file instead
of the key", and claimed the register "was written second and found them". Both
statements were false, and the second one was self-flattering in the direction
`CLAUDE.md` No.2.12 warns about. What actually happened:

The survey loop that collected the schedules for this table ran, per file:

```sh
cal=$(plutil -extract StartCalendarInterval json "$f" 2>/dev/null | head -c 90)
```

**`plutil -extract` writes its result back into the file unless `-o -` is
given.** Four seconds later `com.harbor.{cu-doctor,judge,usage,usage-sessions}`
were 22 bytes each, holding only the JSON of the key that had been extracted —
`{"Hour":8,"Minute":47}` and its three siblings. `pulse` and `fleet-snapshot`
survived only because they schedule on `StartInterval`, so the extract matched
nothing and wrote nothing.

Reproduced on a throwaway plist the same day: 446 bytes in, 22 bytes out,
byte-identical in shape to the four casualties.

Recovery was a single `cp` because this repo carries the canonical plists in
`launchd/`, and the truncated files happened to preserve the one field the
repo copies also carry, which made the match checkable rather than assumed:

```sh
cp launchd/com.harbor.{cu-doctor,judge,usage,usage-sessions}.plist \
   ~/Library/LaunchAgents/
```

All four verified `cmp`-identical to the repo copies afterwards. (That was before the plists became
templates, harbor#630: today the same recovery renders each one,
`sh bin/launchd-render.sh launchd/<id>.plist > ~/Library/LaunchAgents/<id>.plist`, and a plain `cp` would
install the placeholders.)

Three things this is recorded for:

1. **`plutil -extract` and `-replace` write in place by default.** Any read of a
   plist field in a script needs `-o -`. Reading is not a safe default here.
2. **The damage was invisible while it mattered least.** launchd keeps the job it
   loaded, so all four kept their correct in-memory definitions and `launchctl
   list` looked normal. The loss would first have shown at reboot, as four
   checks that silently stopped existing. A register that lists what *should* be
   scheduled is how that gets caught; `launchctl list` is not.
3. **A cause written from the shape of the evidence is a hypothesis.** The
   `plutil -replace` story fit the damage perfectly and was wrong. The
   transcript settled it in one grep, and the grep should have come first.

## Adding a check

1. Stamp every line the check emits with `[check:<id>]`.
2. Add a row here before scheduling it, not after.
3. Give the row a real `red means` — if you cannot say what a red obliges
   someone to do, the check is not ready.
4. Verify it goes red on purpose: break the thing it guards, watch it fire,
   restore. A check that has never been seen red is not a check.
5. Give it a Platforms row. A launchd job that should run on Linux too gets its
   `systemd/harbor-<id>.service` and `.timer` beside its plist.
